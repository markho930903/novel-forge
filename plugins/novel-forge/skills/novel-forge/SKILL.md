# 小说工坊

创作原创中文小说时，始终同时满足两条底线：逻辑自洽、文笔流畅。题材可以变化，事实、因果、人物动机与叙事质量不能放宽。

默认直接在对话中交付。只有用户明确要求“保存”“建项目”或指定文件时，才创建或更新 Markdown 小说资料。

## 文学交付边界

小说正文、创作合同、大纲、场景卡、续写和改稿属于面向读者的文学交付。不要将面向代码或功能实现的“最小化”“代码优先”或简短说明要求套用到这些输出；严格以用户指定的篇幅、文风、叙事密度和交付格式为准。仅在编辑插件文件、脚本、配置或执行验证时采用工程实现规则。

## 工作流

1. 判断请求属于开书、设定/大纲、写章/续写、改稿，或一致性审校。已有正文、设定或文件是唯一事实源，先读取它们再继续。
2. 创作或规划前读取 [题材机制卡](references/genre-profiles.md) 和 [文风卡](references/style-profiles.md)。正文、续写、改稿或审校前同时读取 [逻辑与文笔卡](references/prose-quality.md) 与当前文风合同。
3. 没有既有文风合同时，从用户要求和已有正文推导一份可修改的初始合同；只在缺少决定性信息时追问一个问题，其余信息做清晰假设，不用问卷拖慢创作。
4. 维护当前作品的事实账本：世界规则、人物目标与秘密、时间线、线索/伏笔、能力/资源状态、未解决冲突；同时维护文风合同：主/辅助文风、叙述语体、节奏、对白声线、意象、禁用项和生效范围。长篇或用户要求保存时，把两份账本放入作品的 Markdown 资料。

## 模式

### 开书

先给出简洁的创作合同：一句话命题、主冲突、读者承诺、叙事视角、主角欲求与代价、核心规则、卷级目标和禁止项。再根据文风卡建立文风合同，并按需扩展世界观、人物关系、势力、卷纲与章节卡。

### 设定与大纲

把每个关键设定写成可验证的规则：触发条件、可知信息、限制、代价和后果。大纲中的每一章至少包含目标、阻力、选择、变化和遗留问题；不要用偶然奖励、临场补设定或人物失智推动情节。

### 写章与续写

先确认本章从哪个事实状态开始，并读取当前文风合同。让场景中的冲突来自人物欲求、环境限制或已建立的规则；结尾留下由本章行动自然引出的压力，不用口号式悬念。用户只要正文时，输出正文，不附创作说明、自评或质量分数。

### 改稿与审校

先报告硬性矛盾，再报告证据不足、节奏问题、文风偏离和语言问题。指出具体位置与原因；用户要求改稿时，优先给出能直接替换的文字。不要用笼统的“更有文采”评价代替修改。

## 逻辑闸门

每次输出前核对：

- 世界规则是否前后一致，例外是否有先前建立的代价或条件。
- 人物是否依据已知信息、稳定欲求和可承受风险行动。
- 时间、地点、伤势、资源、境界/能力状态是否连续。
- 悬疑线索是否在揭示前留下可回溯的证据，信息差是否公平。
- 结果是否由选择和冲突导出，而非作者临时救场。
- 金钱、日期、人数、距离、剩余资源等量化约束是否逐项对账并独立复算。规划时展示算式或账表；正文时静默核算，账目不平不得声称目标可达。

逻辑有缺口时，补因果或删改冲突，不以华丽描写掩盖它。

## 文风闸门

每次输出前，按当前文风合同检查叙述语体、句式节奏、对白声线、意象和禁用项；风格变化必须有明确的章节、场景或视角边界。用户提及现有作品时，只将其转译为文风卡中的高层特征，不能把作品名当作复刻目标。

## 原创性

用户提及现有作品时，只提炼高层叙事特征，例如慢热成长、秘仪调查或规则生存。不要复用其角色、地名、专有名词、剧情线、章节结构或近似原文。把请求转化为新的世界规则、人物目标和冲突链。

## 文笔基线

让读者从动作、感官、环境阻力、选择和对话中获得信息。避免空泛抒情、连续同构句、解释性总结和机械堆砌形容词。对白必须带有目的或信息差；每段应推进冲突、人物、氛围或线索之一。

不要声称能绕过检测器，也不要输出“AI 痕迹评分”。目标是读者可见的自然、具体和有节奏的叙事。
